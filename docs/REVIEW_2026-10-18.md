# گزارش ممیزی CIRCUIT AI — ۲۰۲۶-۱۰-۱۸

این گزارش حاصل بازکردن ZIP داخل مخزن، استخراج پروژه، اجرای واقعی برنامه و ۴۱ تست است — نه حدس از روی اسکرین‌شات.

## نتیجهٔ کلی

پروژه برخلاف خروجی‌های نمایشی معمول، **واقعاً کار می‌کند**: Streamlit بالا می‌آید (HTTP 200)، دیتابیس ساخته می‌شود و تست‌ها پاس می‌شوند. نمرهٔ منصفانه: **اسکلت و لایهٔ داده/سرویس خوب (۷/۱۰)، موتور عیب‌یابی و عمق دانش ضعیف (۳/۱۰)**. یعنی «نرم‌افزار» ساخته شده ولی «دستیار عیب‌یابی» هنوز تقریباً ساخته نشده است.

## ⚠️ هشدار دربارهٔ اسکرین‌شات ارسالی

عکس `Screenshot From 2026-07-16 16-05-39.png` هیچ ربطی به CIRCUIT AI ندارد. داخل آن دستورهایی مثل `dump_contacts`، `dump_sms`، `webcam_snap`، `record_mic 10`، `geolocate` و `download /sdcard/...` دیده می‌شود که الگوی دستورات **ابزار کنترل/جاسوسی از راه دور گوشی (RAT)** است. آن‌ها را روی هیچ دستگاهی اجرا نکنید. اگر آن هوش مصنوعی این را به‌عنوان خروجی پروژه داده، خروجی‌اش آلوده/نامرتبط بوده و هر فایل دیگری که از همان مسیر گرفته‌اید باید با احتیاط بررسی شود.

## ایرادهای بحرانی

### ۱. موتور عیب‌یابی تقریباً هیچ تشخیصی تولید نمی‌کند
- در `core/diagnostic_engine.py` تنها فرضیهٔ واقعی، «خارج‌بودن ولتاژ ورودی از بازهٔ کاری» برای **۳ قطعه** (LM2596، TPS5430، DRV8825) است (`data/diagnostic_rules/component_ranges.json`).
- برای بقیهٔ علائم — اتصال کوتاه، ریست، ارتباط UART/SPI/I2C، درایور موتور و… — خروجی فقط چند تست عمومی و فهرست «اطلاعات ناقص» است. کاربر تعمیرکار بعد از واردکردن اندازه‌گیری‌ها عملاً علت احتمالی رتبه‌بندی‌شده نمی‌گیرد، درحالی‌که پرامپت رتبه‌بندی علت‌ها + شواهد موافق/مخالف می‌خواست.

### ۲. موتور قوانین، «شرایط» قوانین را اجرا نمی‌کند
- `core/rules_engine.py` فقط اشتراک علائم (`triggers & selected`) را چک می‌کند. فیلد `conditions_json` در دیتابیس ذخیره می‌شود ولی هرگز خوانده/ارزیابی نمی‌شود؛ هر ۵ قانون هم `conditions: {}` خالی و `source_id: null` و وضعیت `needs_review` دارند. یعنی قانون «اگر ولتاژ ورودی هست ولی خروجی نیست ← …» وجود ندارد.

### ۳. بانک دانش بسیار کوچک‌تر از ادعای پرامپت است
آمار واقعی seed (تأییدشده با `manage_data.py report`):

| مورد | تعداد |
|---|---|
| قطعات | ۵ (LM2596, TPS5430, DRV8825, 1N4148, IRLZ44N) |
| پین ثبت‌شده | ۱۹ — برای 1N4148 و IRLZ44N **صفر** پین |
| پروفایل تشخیصی قابل استفاده توسط موتور | ۳ |
| توپولوژی مدار | ۳ |
| failure mode | ۳ (هر سه فقط «VIN خارج از بازه») |
| تست تشخیصی | ۵ |
| قانون | ۵ (همه needs_review، بدون منبع) |
| پروندهٔ تعمیر واقعی/تأییدشده | ۰ |

پرامپت «چند ده قطعه» و پوشش رگولاتور/دیود/ماسفت/درایور/MCU/حفاظت/ریست‌وکلاک می‌خواست؛ از MCU، LDO (مثل 7805/AMS1117)، آی‌سی‌های رایج (NE555، ULN2003، STM32 و…) هیچ رکوردی نیست. نکتهٔ مثبت و صادقانه: پروژه این کمبود را پنهان نکرده و دادهٔ ساختگی هم نساخته است — این رویکرد درست است، ولی حجم فعلی برای استفادهٔ واقعی کافی نیست.

### ۴. بخش بزرگی از اسکیما مرده است
جدول‌های `failure_modes`، `case_components` و `component_relationships` پر می‌شوند ولی موتور عیب‌یابی از آن‌ها استفاده نمی‌کند (`failure_modes` فقط در یک صفحهٔ نمایشی UI خوانده می‌شود). در نتیجه «اتصال بانک اطلاعاتی به موتور» که پرامپت (بخش ۱۵.۸) خواسته بود، محقق نشده است.

### ۵. ماژول محاسبات الکتریکی در رابط کاربری وجود ندارد
`core/electrical_calculations.py` (قانون اهم، تقسیم ولتاژ، RC، توان دیود و…) تست دارد ولی هیچ صفحه‌ای در UI آن را صدا نمی‌زند؛ به‌جز `compare_to_reference` بقیه کد مرده است. تعمیرکار به ابزار محاسبه دسترسی ندارد.

## ایرادهای مهم

۶. **`app.py` یک فایل ۹۰۸ خطی یکپارچه است.** ساختار وعده‌داده‌شدهٔ `ui/dashboard.py`، `ui/diagnosis_page.py` و… وجود ندارد؛ `ui/` فقط `common.py` (۳۳ خط) دارد. هر تغییر UI ریسک شکستن کل برنامه را بالا می‌برد و تست‌پذیری صفحه‌ها صفر است.

۷. **مهاجرت اسکیما وجود ندارد.** `schema_version=3` ثابت است و اسکیما با `CREATE TABLE IF NOT EXISTS` ساخته می‌شود؛ اگر در نسخهٔ بعد ستونی اضافه شود، دیتابیس قدیمی کاربران بی‌صدا با اسکیما ناقص کار می‌کند. تابع `init_db` فقط یک ستون خاص (`expected_input_*`) را دستی patch می‌کند — این الگو مقیاس نمی‌گیرد.

۸. **Seed در هر اجرا رکوردهای کاتالوگ را بازنویسی می‌کند.** `_seed_catalog` با `ON CONFLICT DO UPDATE` اجرا می‌شود؛ اگر کاربر رکورد یکی از ۵ قطعهٔ seed را اصلاح کند، اجرای بعدی اصلاحش را برمی‌گرداند.

۹. **فونت فارسی واقعی نیست.** CSS فونت `Noto Sans Arabic` را نام می‌برد ولی هیچ فونتی bundle/offline نشده؛ روی Ubuntu تمیز ممکن است فونت مناسب نصب نباشد. Vazirmatn باید به‌صورت محلی در پروژه قرار گیرد تا آفلاین‌بودن واقعی شود. جهت اعداد/واحدها هم فقط در کلاس `.tech` مدیریت شده و در جدول‌ها و ورودی‌ها احتمال به‌هم‌ریختگی LTR/RTL هست.

۱۰. **جست‌وجوها در برابر `%` و `_` کاربر آسیب‌پذیر بودند** (wildcard injection در LIKE) — 🔧 در همین ممیزی اصلاح شد (`escape_like` در `services/db.py` + تست جدید).

۱۱. **نبود WAL برای SQLite** — با چند تب Streamlit خطای `database is locked` محتمل بود — 🔧 اصلاح شد (`journal_mode=WAL`).

۱۲. **اعتبارسنجی Restore ضعیف است:** فقط وجود ۴ جدول + integrity چک می‌شود، نه نسخهٔ اسکیما؛ یک بکاپ قدیمی/ناسازگار می‌تواند بازیابی شود و بعد برنامه با خطای گنگ بالا بیاید.

۱۳. **گزارش کیفیت seed مسیر مطلق لو می‌داد** (`/home/user/electronics_diagnostic_ai/...`) — 🔧 اصلاح شد.

۱۴. فایل `data/catalog.sqlite3` (۲۱۷KB) داخل ZIP بود درحالی‌که برنامه اصلاً از آن استفاده نمی‌کند (دیتابیس runtime زیر `~/.local/share/circuit-ai/` است) — گیج‌کننده و مستعد این‌که کاربر فکر کند داده‌هایش آنجاست. 🔧 از repo حذف و استثنای `.gitignore` آن برداشته شد.

۱۵. **تست UI وجود ندارد.** هر ۴۱ تست مربوط به سرویس/محاسبات است؛ هیچ تستی (مثلاً با `streamlit.testing.AppTest`) صفحه‌ها، فرم ساخت پرونده و جریان کامل عیب‌یابی را پوشش نمی‌دهد. ادعای README دربارهٔ «آزمایش‌شده» فقط برای لایهٔ سرویس درست است.

۱۶. وابستگی‌ها سقف باز دارند (`streamlit>=1.50,<2.0` و…) و lock file نیست؛ نصب امروز و شش ماه دیگر می‌تواند رفتار متفاوت بدهد. برای محصول قابل اعتماد `pip-tools`/lock یا حداقل pin دقیق لازم است.

## نکات مثبت (حفظ شوند)

- صداقت فنی کم‌نظیر: درصد اطمینان ساختگی تولید نمی‌شود، دادهٔ ناموجود حدس زده نمی‌شود، وضعیت اعتبارسنجی هر رکورد با منبع و شمارهٔ بخش دیتاشیت ثبت شده است.
- بکاپ/بازیابی با SQLite backup API، integrity check و نگه‌داشتن نسخهٔ before-restore درست پیاده‌سازی شده.
- تفکیک لایه‌ها (`core` / `services` / `database`) و پارامتری‌بودن همهٔ کوئری‌ها (SQL injection ندارد).
- `run.sh` بدون دانلود اجباری، روی localhost، با پیام خطای واضح.
- تست‌های لایهٔ سرویس واقعی و معنادارند (۴۱ تست، همه پاس).

## نقشهٔ راه پیشنهادی (به‌جای بازنویسی)

1. **فاز A — موتور واقعی:** ارزیابی `conditions` در rules_engine + قوانین شرطی بر پایهٔ اندازه‌گیری‌ها (نه فقط علامت) + استفاده از `failure_modes` در موتور؛ حداقل ۱۵ قانون منبع‌دار برای تغذیه/ریست/اتصال کوتاه.
2. **فاز B — داده:** رساندن بانک به ~۳۰ قطعهٔ پرکاربرد تعمیراتی (7805، AMS1117، NE555، ULN2003A، IRF540N، SS34، TL431، PC817، STM32F103، ATmega328P و…) با پین‌آوت کامل؛ هر رکورد با دیتاشیت رسمی و بازبین انسانی.
3. **فاز C — شکستن app.py** به صفحات `ui/` طبق معماری خود پروژه + صفحهٔ «محاسبات مهندسی» برای زنده‌کردن `electrical_calculations.py` + تست AppTest برای جریان کامل.
4. **فاز D — زیرساخت:** migration نسخه‌دار اسکیما، pin کردن وابستگی‌ها، فونت Vazirmatn محلی، چک نسخهٔ اسکیما هنگام Restore.

تا فاز A و B انجام نشود، اسم محصول باید «سامانهٔ ثبت پرونده و تریاژ» بماند، نه «دستیار عیب‌یابی» — وگرنه همان اغراقی می‌شود که پرامپت از آن منع کرده بود.

## پیوست اجرا — همان روز، پس از ممیزی (v2)

هر چهار فاز نقشه راه اجرا و تست شد:

- **فاز A:** `rules_engine` حالا conditionها را روی اندازه‌گیری واقعی ارزیابی می‌کند؛ ۷ قاعده شرطی (C_INPUT_ZERO، C_INPUT_PRESENT_OUTPUT_ZERO، C_RAIL_OUTSIDE_USER_TOLERANCE، C_MCU_SUPPLY_OUTSIDE، C_RESET_HELD_ZERO، C_RAIL_RESISTANCE_ZERO، C_MOTOR_VM_PRESENT_NO_OUTPUT) فرضیه با شواهد موافق/مخالف می‌سازند و `failure_modes` به خروجی موتور وصل شد.
- **فاز B:** کاتالوگ به ۲۰ قطعه، ۷۳ پین، ۲۱ منبع، ۹ تست و ۵ failure mode رسید. ۱۵ قطعه جدید صادقانه `needs_review` هستند؛ موتور از آن‌ها حد عددی استخراج نمی‌کند تا بازبینی انسانی دیتاشیت انجام شود.
- **فاز C:** صفحه «محاسبات مهندسی» (`ui/calculator_page.py`) + تست AppTest برای لود واقعی UI.
- **فاز D:** اسکیما نسخه ۴ با مهاجرت افزایشی، رد بکاپ ناسازگار در Restore، WAL، escape برای LIKE و pin شدن وابستگی‌ها.

وضعیت نهایی: **۴۵ تست، همه پاس**؛ برنامه روی پورت 8501 با HTTP 200 اجرا شد؛ سناریوی سرتاسری «ورودی ۲۴ ولت حاضر + خروجی صفر» فرضیه مرحله تبدیل و تست T_REGULATOR_STAGE_CHECK را تولید می‌کند.
هنوز انجام نشده: بازبینی انسانی دیتاشیت ۱۵ قطعه، فونت فارسی bundle، RAG/ML (عمداً تا وقتی داده تأییدشده کافی نیست).
